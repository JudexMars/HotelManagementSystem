# Booking Service

Регистрация и авторизация пользователей, администрирование учётных записей и бронирования. Общий запуск и пример работы — в [README проекта](../README.md). Порт сервиса — 8081; в Docker Compose API доступен через Gateway на порту 8080.

## Регистрация и вход

| Метод | Тело | Ответ |
|---|---|---|
| POST `/api/users/register` | `{username,password}` | 201, новый USER и токен |
| POST `/api/users/auth` | `{username,password}` | 200, пользователь и токен |
| GET `/api/users/jwks` | — | Публичные ключи проверки JWT |

Ответ входа и регистрации содержит `accessToken`, `tokenType: Bearer`, `expiresIn: 3600`, `user {id,username,role}`. Для защищённых методов нужен `Authorization: Bearer <accessToken>`.

Username регистрозависим: 1–100 символов без пробельных. Пароль — 8–72 байта UTF-8. Повтор имени возвращает 409; неверные данные входа — 401. Регистрация всегда создаёт USER, неизвестные поля JSON, включая `role`, отклоняются с 400. Демонстрационные учётные записи приведены в [корневом README](../README.md#демонстрационные-данные).

После изменения пароля старый пароль не подходит для нового входа. Уже выданные JWT сохраняют права до истечения часа, в том числе после изменения роли или удаления пользователя. После общего сброса данных нужно войти заново.

## Администрирование пользователей

Все методы требуют ADMIN.

| Метод | Запрос и результат |
|---|---|
| POST `/api/users` | `{username,password,role}` → 201 `{id,username,role}` и Location |
| GET `/api/users/{id}` | Пользователь; неизвестный/удалённый — 404 |
| GET `/api/users?page=0&size=20` | Страница пользователей, порядок username/id |
| PUT `/api/users/{id}` | `{username,role,password?}` → обновлённый пользователь |
| DELETE `/api/users/{id}` | 204; повтор — 404 |

Отсутствующий или null password сохраняет прежний пароль. Удаление пользователя не отменяет брони и не освобождает имя для повторной регистрации. Конфликт конкурентного изменения возвращает 409. Пароли и их хеши в ответы не включаются.

## Бронирования

USER работает со своими бронями; ADMIN может читать и отменять любые, но создаёт только для себя. Чужая бронь для USER возвращает 404. Номер, даты и владелец созданной брони не редактируются.

| Метод | Назначение |
|---|---|
| POST `/api/bookings` | Создать бронь; обязателен Idempotency-Key |
| GET `/api/bookings/{id}` | Прочитать бронь и состояние компенсации |
| GET `/api/bookings?page=0&size=20&userId=<uuid>` | История с необязательным фильтром пользователя |
| DELETE `/api/bookings/{id}` | Отменить бронь до даты заезда |
| GET `/api/bookings/recommendations?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD&hotelId=<uuid>` | Свободные номера по возрастанию timesBooked, затем id |

### Создание и автоподбор

Ручной выбор: `{autoSelect:false,roomId,startDate,endDate}`. Автоподбор: `{autoSelect:true,hotelId,startDate,endDate}`. `autoSelect` обязателен; в ручном режиме hotelId игнорируется, в автоматическом — roomId. Даты ISO, заезд не раньше сегодня UTC, выезд строго позже. Владелец определяется токеном.

Успех — 201, `status=CONFIRMED` и Location `/api/bookings/{id}`. Ответ содержит id, userId, roomId, hotelId, startDate, endDate, createdAt, status, step, attemptId, compensationStatus. При автоподборе roomId может быть null, пока номер не выбран.

В рекомендациях hotelId необязателен, прошлый период допустим. Неизвестный отель — 404. Просмотр не удерживает номер. Автоподбор перебирает кандидатов при конфликте занятости; отсутствие свободного номера возвращает 409 ROOM_UNAVAILABLE. Строгая равномерность при параллельных бронированиях непересекающихся дат не гарантируется.

### Повтор запроса

Idempotency-Key — регистрозависимая строка из 1–128 печатных ASCII-символов без пробелов. Ключ действует в пределах пользователя до сброса H2. После потери ответа повторите прежний ключ и параметры; для новой брони нужен новый ключ.

Повтор возвращает ту же бронь: 202 для PENDING, 200 для CONFIRMED/CANCELLED. Изменение значимых параметров с прежним ключом — 409 IDEMPOTENCY_CONFLICT. Отменённая бронь не создаётся заново. Отсутствующий или неверный ключ — 400.

### Отмена и ошибки оформления

Новая отмена разрешена только до даты заезда UTC, иначе — 409 CANCELLATION_TOO_LATE. Повтор отмены уже CANCELLED допустим и после этой даты. Ответ содержит бронь и Location: 200 при `compensationStatus=DONE`, 202 при `PENDING`. В последнем случае освобождение продолжается фоном; результат проверяется через GET.

При сбое оформления бронь отменяется. Если ошибка произошла после создания записи, ответ содержит bookingId, status, compensationStatus и Location. Основные коды: 409 — конфликт бронирования, 503 — недоступность Hotel или ошибка протокола, 504 — тайм-аут, 502 HOTEL_ACCESS_DENIED — отказ служебного доступа к Hotel. CANCELLED/PENDING ещё не означает, что номер освобождён; это подтверждает только DONE. Подробности — [сага](../docs/adr/003-booking-saga.md).

### История и страницы

Списки пользователей и броней возвращают `{items,page,size,totalElements,totalPages}`. Page начинается с нуля, size — 1–100, по умолчанию 20. Смещение page × size не должно превышать 2 147 483 647. Неверная пагинация — 400, страница за концом списка пуста.

История отсортирована по createdAt DESC, id DESC. USER видит свои записи; чужой userId даёт 403. ADMIN без фильтра видит все брони, с фильтром — брони выбранного пользователя; неизвестный userId даёт пустой список. История сохраняется после удаления каталога или пользователя и читается без обращения к Hotel.

## Хранение и проверка

H2 in-memory хранит пользователей, брони и состояние оформления. [Миграции](src/main/resources/db/migration) описывают поля, связи, индексы и ограничения. Потеря данных требует общего сброса системы.

```sh
./gradlew :booking-service:test :booking-service:bootJar spotlessCheck
```

OpenAPI через Gateway: `/v3/api-docs/booking`. Сквозные проверки — в [verification](../verification/README.md).
